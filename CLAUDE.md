# mktask

Work task prioritizer built on [mkio](https://github.com/markuskimius/mkio) (config-driven backend: SQLite + WebSocket services) and [mkui](https://github.com/markuskimius/mkui) (config-driven Web Components workspace). Sibling of [mkfix](../mkfix), whose structure this repo copies.

## Quick start

```bash
pip install -e '.[test]'
mktask                    # http://127.0.0.1:8080/, mktask.db in cwd
mktask -d :memory: -p 9090 --user mark
mktask --files ~/refs     # uploaded reference files (default: <db>.files beside the database)
python -m pytest
```

## Architecture

- `serve()` in `__main__.py` loads `mktask.toml` via `mkio.config.load_config`, injects `version = __version__`, resolves `"__mkui__"` to `mkui.static_dir` and relative static and config dirs against the TOML's directory, sets `services.tasks.prefix` from `user` (`--user`, default `getpass.getuser()`), resolves the files directory (`_files_dir`: `--files`, else `<db_path>.files`, else a temp dir for `:memory:`), creates it, adds it as the `/files` static route and as `services.tasks.files_dir`, probes the port (`_check_port`), then `create_app(cfg, routes=[("POST", "/files", …)]).run()`. A startup hook prints the banner. Neither the username nor the files dir is a top-level mkio config key (unknown keys warn); tests that call `serve()` chdir to a scratch dir because it creates the files directory.
- `POST /files` (`_upload_handler`): raw body, `Content-Type` → extension (`_EXTENSIONS` overrides, then `mimetypes`, else `.bin`), streamed under `MAX_UPLOAD` (20 MB) rather than aiohttp's 1 MB `client_max_size`, written as `<sha256>.<ext>` (temp + `os.replace`), returns `{href, mime, size}`. Content-addressed: repeats dedupe, no client name reaches the filesystem. The route never writes a row; the client follows with `add_ref`.
- `_check_port` runs before `create_app`: a bind failure inside `app.start()` happens after the startup hooks have opened the database, whose aiosqlite threads then keep the process alive after the traceback. The probe turns that hang into an exit-1 with a one-line error.
- `_find_config()` prefers `./mktask.toml` over the packaged one, so a user can copy it out (with `static/` and `config/`, which resolve beside it) and customize it.
- **The UI is written as TOML and served as JSON** (0.19.0; it was `static/app.json`): the `[config]` route in mktask.toml makes mkio answer `/config/app.json` from `config/app.toml`, parsed per request (a syntax error is a 500 there). `index.html` fetches it with `cache: "no-cache"` and calls `setConfig`; mkui only sees JSON. **TOML has no null**, so `""` stands in (the two `state` selections, which mkui overwrites with `null` once the panes publish; the `mkio.connected` colours). **A `[table]` under an `[[array]]` belongs to the element above it** — a moved block changes owner silently. An inline table must fit on one line. With no `app.toml`, an `app.json` there is served as is.
- `mkio.expect` in app.toml pins `name` and `expr` only. Never pin `version` — every release would then show "Server mismatch". `expr` is an exact match on mkio's `LANGUAGE_VERSION`, so an mkio language bump shows the same banner until the pin follows it; `test_ui_config.py` holds it to the installed mkio, and the mkio floor to 1.6.0 (the first to send `Cache-Control: no-cache`).

## Vocabulary

A task is **split** into **child** tasks (never "subtask"); a child can be split again, to any depth. A task is **moved** when its parent changes: under another task, or to the **top level** (no parent). A task is **open** or **complete** (never "done"). Its identifier is its **Task ID** (never "ID"). A task has **references** (never "attachment"): a **link** (a URL), a **text** snippet, a **file**, or a **task reference** with a **relation**; the other end is the **related task**. "Link" means only a URL reference (never "task link" or "linked task"; two tasks are **related**); the stored `kind` stays `url`, displayed as `link`. A text reference is a **snippet**, **plain** or **Markdown** (its **format**); a task's notes have a format too. A relation is a **pair of wordings**, **forward** ("blocks", this task to that one) and **backward** ("blocked by"), equal for a symmetric relation ("relates to"); the user defines them. A task is **assigned to** an **assignee**, named by the **Assigned To** picker; the names it offers are a list the user keeps, and a name is **taken off the list** (never "deleted from the tasks") — every task already assigned to it keeps it. A task with no assignee is **unassigned**, which in the picker is mkui's own blank row. Every change to a task or a reference makes a new **version** of it; **undo** and **redo** step it back and forth along its versions (never "revert"). What happened to a task — created, moved, ref_added — is its **activity**, kept apart from its versions. `test_ui_config.py` fails on the word "done" anywhere in app.toml (comments included) or mktask.toml, and on "task link" or "linked" in app.toml.

## Data model

`tasks`: `task_id` (TEXT PK), `parent_task_id` (`''` = top level, else the parent's Task ID), `title`, `notes`, `notes_format` (`plain` | `markdown`, as a snippet's `format`), `status` (`open` | `complete`), `importance` and `urgency` (1..5), `due` (ISO date or `''`), `assigned_to` (a name from `assignees`, or `''`), `created_at` / `updated_at` / `completed_at` (UTC `YYYY-MM-DD HH:MM:SS`, matching SQLite's `CURRENT_TIMESTAMP`). Timestamps on update come from the client: buttons and the Edit dialog send `${TIME(NOW(), '%Y-%m-%d %H:%M:%S')}` (mkio expression stdlib, UTC by default) because mkio transaction `defaults` are static values.

`relations`: `relation_id` (AUTOINCREMENT), `forward`, `backward` (= `forward` when symmetric), `notes`, timestamps. Every wording is unique across both columns, case-insensitively (service-enforced; mkio has no unique index). Seeded from `relations.json` (beside the TOML; mkio resolves `seed` against the config's directory and seeds only when it first creates the table). `SEED_RELATIONS` in services.py is the path; tests read it for the wordings.

`assignees`: `assignee_id` (AUTOINCREMENT), `name`, `notes`, timestamps. Unique across the table, case-insensitively (service-enforced, as for relations). **It is the dropdown and nothing else.** `tasks.assigned_to` holds the name itself, so the list can be edited without reaching into a single task: taking a name off it stops the picker offering the name, and renaming one changes what the picker offers next time — neither rewrites a task, which is the one place mktask deliberately parts company with `relations` (whose wording a task reference is *looked up* by, so a rename there must rewrite `task_refs`). The table starts empty; the picker is its front door (see `_assignee_steps`).

`task_refs`: `ref_id` (AUTOINCREMENT), `task_id` (the owner), `kind` (`url` | `text` | `file` | `task`), `relation` (task references only: a **wording** from `relations`, e.g. `blocked by`, else `''` — the wording itself, not an id, so no join is needed and a rename rewrites the rows), `label` (what the UI shows), `href` (`url`: the URL; `file`: `/files/<sha256>.<ext>`; `task`: the related task's Task ID; `text`: `''`), `body` (`text` only), `format` (`plain` | `markdown`; a snippet's alone, every other kind is `plain`), `mime` (`file` only), `created_at` / `updated_at`. One-to-many: a reference belongs to one task; the same URL or file under two tasks is two rows, and for files that is what keeps a shared file alive (`_unlink_orphans` counts rows by `href`). **A task reference is two mirrored rows**, one per side with the pair's two wordings, so a pane filtered on `task_id` shows every task reference of a task from its own side with no client logic. Files live on disk, never in SQLite.

`tasks.last_event` is the most recent thing to have happened to the task, in words — "Created", "Split into Wire the pane", "Attached a file: shot.png", "Related: blocks TKMA00000002", "Moved under TKMA00000007". `event_phrase(action, detail, kind)` in services.py builds it, and `_event()` carries it alongside the `task_events` row it makes, so an event and its Last Event are never worded twice. Because `tasks` is versioned it rides along in every recorded version, which is what makes a task's history say what each version was *about* — `_mkio_op` only ever says `insert` or `update`.

**How `last_event` is written matters.** For an op that already writes the task row it is one of that op's own fields (`_rows_for` puts it there); a separate update in the same transaction would record a *second* version of the same task. For an op that does not — a reference added, edited or deleted, and the parent's side of a split — it is the `touch` op, one per task, applied through `_touch_steps(events, wrote)` where `wrote` names the tasks the op wrote itself. **The touch is what puts reference events in a task's recorded history**, and because it carries the same `_mkio_ref` it is part of the same action to undo: undoing a reference steps the task's version back with it. **The undo/redo hook never touches it** — an undo restores the version's own `last_event`, and writing one would extend the chain past the cursor and discard the redo branch the undo had just made.

`counters`: one row `name = "task"`, `last` = the last Task ID number issued.

**`tasks` and `task_refs` are `versioned = true`.** mkio gives each a `_mkio_version` counter and a companion `tasks__history` / `task_refs__history` keyed `(pk…, _mkio_version)`, holding every version's whole row stamped with `_mkio_op` (`insert` / `update` / `baseline`), `_mkio_ref` (the transaction), `_mkio_user` and `_mkio_service`. The live row's counter is a **cursor** into that chain: versions above it are the redo branch, and writing at version V discards V and above — an edit after an undo abandons what was undone. **A delete is a real delete**: mkio drops the row's history with the row, which is why deleting is the one thing here that cannot be undone. `_mkio_user` stays NULL (no auth); the actor is in `task_events` instead. Nothing in mktask.toml declares these tables — mkio derives them, and `auto_migrate` creates them.

`task_events`: `event_id` (AUTOINCREMENT), `task_id` (the owner), `action` (`created` | `split_from` | `split_to` | `edited` | `moved` | `completed` | `reopened` | `ref_added` | `ref_edited` | `ref_deleted` | `undone` | `redone`), `detail` (one line — the new title, the new parent, the reference's label), `ref_id` (the reference an event concerns, `0` when there is none or when an insert's key is not yet known), `actor` (`--user`), `at`. **Deliberately not versioned**: it is append-only, it must survive the redo-branch truncation a post-undo edit performs, and it records events that change no row of their own. The transaction ref is mkio's own `_mkio_ref` column, so no column of ours repeats it. A task delete takes its subtree's events with it.

**Task IDs** are `TK` + two prefix letters + a decimal sequence padded to at least 8 digits (`TKMA00000001`; pattern `^TK[A-Z0-9]{2}\d{8,}$`). The prefix is `user_prefix(username)`: alphanumerics, uppercased, first two, `X`-padded. The sequence is global (one counter regardless of prefix), never reused after a delete, and never wraps: `TKMA99999999` → `TKMA100000000`. Nothing may depend on id order (text order breaks at the rollover); chronology is `created_at`.

The `score` column is virtual: `values.score = "importance * urgency"` on the `tasks` pane. It is the placeholder for the real prioritization model (see PLAN.md, Deferred).

**No migrations before 1.0.** A schema change means "delete mktask.db"; the README says so. `auto_migrate = true` only covers additive changes — which everything since has been: an existing database gains `last_event`, `task_events` and the two history tables (0.8.0), then `tasks.assigned_to` and the `assignees` table, on first start, and mkio records every row already there as a `baseline` version 1 so a first edit is undoable. `TestUpgrade` in test_server.py builds a pre-0.8.0 database from the current config minus everything added since and boots the server on it, so that promise cannot rot.

## Services (`mktask.toml`)

- `tasks` — `protocol = "mktask.services.TaskTransactions"`, a `TransactionService` subclass; the ops stay in the TOML. `add` and `split` are two steps (upsert `counters.last`, insert the task) plus their events: the class takes the next number from an in-memory counter (seeded in `start()` from `counters`, else from the largest existing Task ID), injects `task_id` and `last` into the data, rejects a request that carries its own `task_id`, and rejects a `split` whose `parent_task_id` is not an existing task (a rejected request consumes no number). Every op goes through `_guarded` → `_op_<name>`, `add` and `split` included, replying mkio-style (`KeyError` → "Missing required field", anything else → its message). **Events are always filled in Python, never bound.** A `bind`'s `"$N.field"` is an absolute position in the request's op list, and `_steps` repeats an op set once per row for a cascade or a task reference's mirror, so a bound event would name the first row's write for every row; `_submit` and `_submit_each` take an `events=` list and append `add_event` steps to the same transaction (on `_submit_each` they ride the first request; one batch, one commit). `complete` runs the single-row op over the subtree (recursive CTE, parents first), `reopen` over the task and its ancestors, in one `writer.submit` (`_submit`) so the change bus announces every RETURNING row. **Deletes go one request per row** (`_submit_each`, gathered so they land in one batch): mkio announces a delete with the request's `data`, so one request for a subtree would announce the parent's Task ID for every row. `delete` also removes every reference the subtree owns or is referenced by, then unlinks orphaned files. `add`, `split` and `edit` check `notes_format` (`_with_notes_format`: one of `REF_FORMATS`, else `plain`; an `edit` that names none keeps the task's own, which is why the op declares no default). `edit` is the plain update plus a `relabel_ref` per task reference that points at the task (same submit). `edit_notes` and `edit_snippet` are the Text pane's saves: the text and its format alone (see UI). `move` rewrites one row's `parent_task_id` (`''` or `TOP_LEVEL` = top level; a Task ID encodes no hierarchy, so nothing else is rewritten and the subtree follows for free): it refuses self, an unknown parent, and a parent inside the moved subtree, refuses a move that would leave a task reference inside one tree (`_check_no_links_merge`, as `add_ref` would; the message names the first and counts them), and appends the `reopen` steps for the complete new ancestors when the moved subtree holds open work, in the same submit. `add_ref` requires the owning task, fills a missing label (`default_label`; for Markdown the first line through `plain_text`, which drops the markers and link targets, a fence line skipped), forces `href`/`body`/`format` by kind (`_format_of`: a snippet's checked against `REF_FORMATS`, everything else `plain`), and for kind `task` checks the relation is a known wording (`_inverse` looks the pair up; the mirror gets the other wording), self, target, same tree (the two `_ancestors_and_self` chains must end in different roots; ancestor and descendant get their own messages), and duplicate, then inserts the row and its mirror; `edit_ref` on a task reference takes only `relation` and rewrites both halves (`_mirror` finds the other), on a file keeps the `href`, on a snippet blanks it and takes `format` (an edit that names none keeps the snippet's own); `delete_ref` deletes the mirror too, then the file if nothing names it. `add_relation` / `edit_relation` (`_relation_data`: trim, backward defaults to forward, uniqueness excluding self) / `delete_relation` (refused while any task reference carries either wording, count in the message); a rename rewrites `task_refs.relation` through `reword_ref` in the same submit. `add_assignee` / `edit_assignee` / `delete_assignee` manage the Assigned To list and **touch no task at all**. `add_assignee` is also a *step* `add`, `split` and `edit` append through `_assignee_steps`: a name the list does not hold joins it in the same transaction. Only a name the write *changes*: `_op_edit` / `_op_split` pass the previous value (the task's own, the parent's) as `previous`, so a retired name on an edited or split task does not come back. A listed spelling wins ("alice" over "Alice"). mkio skips op validation for dotted protocols; the tests catch a bad field name.
- `all_tasks` — query on `tasks`, `filterable = ["status", "parent_task_id"]`. The blotter subscribes to this, and so does the Detail pane's `task-refs` widget (unfiltered, `fields = task_id/parent_task_id/title`) for the parent/child edges its subtree needs.
- `task_refs` — query on `task_refs` **joined to `tasks`** for `task_title` (`r.*` + `LEFT JOIN tasks`, `watch_tables = ["task_refs", "tasks"]`), `filterable = ["task_id", "kind", "relation"]`; the References pane subscribes, and so does the Detail pane's `task-refs` widget (filtered to the selected task's subtree: `task_id == 'X'` for one, `CONTAINS([…], task_id)` for many — `filterable` gates *whether* a filter is honoured, not which expression, and a filtered query still announces a delete of a row it had sent, which is how a deleted reference leaves the widget). `all_relations` — query for the Relations pane; `all_assignees` — query for the Assignees pane. The Assigned To picker has **two** reqreps: `assignee_options` (no params — `__new__` "— New name —" first, then every name alphabetically) for the New dialog, and `task_assignee_options` (`:task_id`) for Edit and Split, which `UNION`s in that task's own `assigned_to` so a name taken off the list still shows on the task carrying it. They cannot be one service: **an `optionsFrom` param that resolves to `''` empties the whole list** (mkui's `hasUnresolved`), and the New dialog has no task to name. Two reqreps feed the Reference dialog's `optionsFrom`: `relation_options` (every wording as `value`/`label`, `UNION` collapsing a symmetric pair to one) and `task_options` (open tasks outside `:task_id`'s tree). `move_options` feeds the Move dialog's parent picker: `__top__` (`— Top level —`, ordered first) plus every open task outside `:task_id`'s subtree. **The top level is a sentinel, not `''`**: an untouched dialog sits on mkui's own blank `""`, which would then promote the task. `TOP_LEVEL` maps it back to `''`; `required` refuses the blank. `ref_owner_options` feeds the reference dialogs' Task picker: every task, open first, labelled by Task ID and title, **no params** (a `''` param would empty it). `test_ui_config.py` holds reqreps and the names using them to each other. **A joined query updates live**: mkio re-reads a changed reference through the sql (an insert arrives with `task_title`) and, with `tasks` in `watch_tables`, re-runs it after a task changes and sends only the rows that differ — a rename is one update per reference the task owns, the reference's own version unmoved. The sql must keep `ref_id` in the result (`r.*`; `test_ui_config.py` pins it), or mkio serves bare rows with a startup warning. `_mkio_row` becomes `[ref_id, task_id]`, and a delete goes out with the cached row, so clients keyed on it still find it.
- `task_activity` — query on `task_events`, `filterable = ["task_id", "action"]`; the Activity pane subscribes and follows the Tasks selection through table linking, the way the References pane does. `task_versions` / `ref_versions` — queries on `tasks__history` / `task_refs__history`, filterable on the base primary key, which is what mkui's history pane narrows to one record with. `task_version_state` / `ref_version_state` — reqreps returning `{ current, top }` so mkui can tell whether a redo is there to offer; written as two subqueries so they answer with one row even when the record has been undone out of existence (`current` NULL). `task_version_chain` / `ref_version_chain` — reqreps returning one record's whole chain, which mkui reads to spell out what a step will change in its confirmation. mkio never advertises a history table, so these services are the deliberate act of exposing it; transaction ops against one are rejected at config load, so the exposure is read-only by construction.
- `mkui_layouts`, `mkui_layouts_list`, `mkui_layouts_get` — verbatim from mkui's scaffold; mktask has no login so every save lands under owner `''`.

## History, undo and redo

**mkio owns the version log and mkui owns the history UI; mktask owns what neither can know.** A `history` block on a table pane (`table`, `key`, `feed`, `versions`, `state`, `columns`, `undo`, `redo`, `confirm`) is all mkui needs to draw the `mkio-history` pane — the versions in a real `mkio-table` with **Diff** and **Blame** panels — plus an Undo and a Redo button on the source pane's toolbar. `table.history` opens it (`{ pane, keys }`, the keys selecting the record first); `workspace.showPaneHistory` registers `_history:<pane>` on demand, titled "History — <title>", one per table pane and re-pointed as the selection moves. **mkui drops an unknown `history` key with a console warning rather than failing**, so `test_ui_config.py` is the only thing that catches a typo in one.

Three things mktask adds:

- **`undo_action` / `redo_action`** (`_step_action`). mkio's `undo`/`redo` op types move **one row's** cursor, keyed by primary key; a mktask action is rarely one row — a task reference is two mirrored rows, completing a task completes its subtree, a move reopens the ancestors it lands under. The group needs no bookkeeping of ours: mkio stamps every row a transaction writes with that transaction's `_mkio_ref` and indexes it, so `_group_ref` finds the ref that wrote the version being stepped off (for a redo, the one *above* the cursor, or version 1 when there is no row) and `_group_rows` takes everything it wrote. **The steps go one request per row**, because the writer reads an undo's key from the request's own `data`, not from its params; they are gathered, so they land in one batch and one commit. `history.undo` in app.toml points at these, never at mkio's own ops — those (`undo_task`, `redo_task`, `undo_ref`, `redo_ref`) exist only for `_step_action` to submit.
- **Three guards** (`_check_step`). A step is refused rather than half-applied when a row of the group has moved past the version the action wrote (`_mkio_version` no longer matches; the test produces this with mkio's raw per-row op), when an undo at version 1 would remove a task that still has children or references (`_check_removable`), or when the version being stepped onto names a parent or a related task that has since been deleted (`_check_restorable`). Messages stay short: mkui clips a dialog's status line to one row.
- **`undo_redo_hook`**, registered in `serve()` through mkio's `on_undo_redo`. Moving a cursor restores the row but not what followed from the write it reverses, and neither of these is on a cursor move's path: a task reference shows the title of the task it points at (refreshed by `_op_edit`, so a step would leave it stale), and the narrative. It relabels through `_relabel_steps`, which **only touches rows whose label disagrees** — a relabel is an ordinary write on a versioned table, so a no-op one would spend a version and discard that reference's redo branch, and being idempotent is what lets the hook run it blindly after a group step that already carried the task reference rows along. Only a `tasks` step is narrated: a reference's own steps are its version history's to tell, and narrating them would put a "redone" in a task's activity for the resurrection `_op_delete` does on its way to deleting a reference for good. A row undone out of existence is not narrated at all — there is nothing left to narrate it against. `cause` is its own recursion guard: the hook's own writes are ordinary ones, so their events carry `cause = None`.

**Deletes are permanent and thorough.** `_op_delete` resurrects (`redo_ref`) any reference of the subtree left as a chain by an undo, so deleting it drops that chain the way mkio drops any deleted row's history; then deletes every reference the subtree owns *or that points at it* (one reach, used for both the live rows and the recorded versions), the tasks, and the subtree's events. `_unlink_orphans` now keeps a file while **either** a live `task_refs` row or a `task_refs__history` row names it — an undone file reference is a chain with no row, and redo has to find its file still there. **Undo never unlinks**; only a delete does.

**No keyboard shortcut.** mkui binds no key to `edit.undo` / `edit.redo` on purpose (shared state); the Edit menu and the toolbar buttons fire them.

## UI (`config/app.toml`)

- **A table pane's `columns` is every column its query returns; `visible` is what it opens on** (and what Reset restores). mkui's Columns picker offers exactly `columns` (`_mkio_*` only when named), so a column left out cannot be shown at all. `test_ui_config.py` fails on a query column missing from `columns` or a pane without `visible`.
- `tasks` pane: `mkio-table` with `tree` on `parent_task_id`/`task_id`, `expand = 0` (opens on the roots, folded; pinned by `test_ui_config.py`. `table.select` unfolds a hidden row's ancestors, so "Go to" and `submit.then` still land; a Split under a folded parent only marks its caret; shift-click on the header caret opens every level, again folds all — mkui 1.13.0, and the Shortcuts box says so), sort `["-score", "created_at"]`, `select.state = "selected_task"`. `assigned_to` is a column, **Assigned To**; `parent_task_id` (**Parent**, off by default) is all a flattened row has to name its parent. `filterScope = "all"` (Branch) makes the default filter `status = ["open"]` test every row while keeping the way to a match, so a complete child under an open parent is hidden and an open child keeps its complete parent visible. Buttons: New, Edit, Move, Split, History, Complete, Reopen, Delete — no Reference: adding one is the References pane's job. **mkui renders a dialog's status line `nowrap` with an ellipsis** — a server refusal longer than the footer is silently cut in half, which is why Move is `width = 600` and `_check_no_links_merge`'s message is as short as it is. **Delete's readonly-line dialog *is* the confirmation** (mkui has no confirm on transaction buttons); red only `when = "enabled"`, no bold, so its width never shifts. No dialog ever sends `task_id` or `last` on add/split.
- **Adding a reference is the References pane's job**: Add Link / Add Text / Reference Task, one dialog each, `kind` hidden and fixed, no `showWhen`. The first field is the Task picker, `task_id` itself: a `select` on `ref_owner_options` with `value = ${state.selected_task.task_id}` — mkui hands every dialog the app state, and a `value` is parked until the fetched list holds it — so it opens on the selected task, stays a picker (the title follows it), and starts on mkui's blank when nothing is selected, which `required` refuses; the buttons take no `unit`. The Reference Task dialog's `_task` picker takes `params.task_id = ${field.task_id}`, refetched as the Task picker moves. `submit.then` fires `table.select` on the Tasks pane with the submitted `task_id`, so a reference filed on another task is shown. **Underscore-named fields are scratch and are never submitted; a field hidden by `showWhen` is not submitted either** — which is why `href`/`body`/`relation`/`label` carry `defaults` on `add_ref`/`edit_ref`. There is no file field in mkui, so files stay with the Detail pane's drop box. Readonly lines carry no `name`.
- **The Assigned To picker is three fields, and mkui's `optionsFrom` is why.** It prepends a blank entry of its own that cannot be removed or relabelled (the `"—"` is hardcoded in `mkui-dialog.js`), and it *cannot be given a value* — it forces the selection back to `""` after every fetch. **That blank is unassigned**: it submits as `''`, which is exactly what the column holds for nobody, so the picker carries one sentinel and not two. `__new__` is the other row, and it reveals the scratch `_new_assignee` box. The scratch `_assignee` picker and `_new_assignee` box feed a hidden, computed `assigned_to` — the `_url`/`_task` → `href` idiom the Reference dialogs use — in all three dialogs. **A `compute` on the picker itself is what preselects it**: computes re-run until they settle and `fetchOptionsFrom` calls `applyDynamic()` when the list lands, so `row.assigned_to` sticks once the option exists — and stops the moment the user touches the field (mkui's `dirty` set). An unassigned task has nothing to stick, so it falls to mkui's blank: right by construction. Split opens on the parent's name, as Importance and Urgency copy. **This is why `task_assignee_options` unions the task's own name in** — a name missing from the options would fall to the blank, and saving would then clear the assignment rather than keep it.
- `assignees` pane: `mkio-table` on `all_assignees`, New / Edit / red Delete, opened from the Configure menu. Its Delete says the tasks keep the name and does **not** say "cannot be undone": nothing is lost.
- **The References and Activity panes follow the Tasks selection through mkui table linking**: `tasks` broadcasts `task_id`, they listen on it, and the selected rows' Task IDs become an include filter on the listener (a selected tree row sends its subtree; nothing selected retracts the filter). All set `link.chips = false` to keep the control chips off the toolbars. Nothing in `refs.js` filters anything — its query is filtered server-side.
- **Snippets and notes are written formatted** (0.21.0): the `richtext` field (`richtext.js`) is a TipTap editor that shows the formatting as it is typed (Cmd/Ctrl+B mid-word, `1. ` starts a list, a toolbar with pressed state, a link box under it rather than a prompt) and hands the dialog **Markdown**, so storage stays text. Add Text, New and Split use it with `format` / `notes_format` hidden and fixed to `markdown`; no syntax line, and Add Text's label has no compute (the server's `default_label` strips the markers). **Edit is three boxes and a hidden field**: a Markdown item opens in `_body_md` / `_notes_md`; a plain one in the `_body_plain` / `_notes_plain` textarea with a **Format** select (Plain text / Formatted, shown only for a plain item: formatted stays formatted), and Formatted shows `_body_converted` / `_notes_converted`, a `literal = true` editor computed from the textarea, which takes the text character for character and hands back escaped Markdown. The hidden `body` / `notes` computes whichever is showing (a snippet's `body` is `''` for every other kind, which `edit_ref` ignores). **The field keeps a set value as given until an edit**, so an untouched Edit sends back exactly what it opened on, and a compute re-set with the same value is no change (it must settle). `setEditable` is called only on a real change and without an update event — an update is an edit, which would re-run the dialog's pass forever. The serializer escapes inline syntax itself; `entry.js` adds `LINE_STARTS` (a paragraph line that would read as a heading, list item, setext underline or indented code) and drops a link outside `SAFE_PROTOCOLS`. A snippet pasted or dropped in the Detail pane is plain. `test_ui_config.py` pins all of it and fails on a dialog field `type` neither built into mkui (`FIELD_TYPES`) nor registered by a module index.html imports.
- `references` pane: `mkio-table` on `task_refs`, `select.state = "selected_ref"`, sorted `-created_at`, **Task Title** (`task_title`, the joined column — not in the `history` block, whose columns are the row's own), **Text** (`body`, after Reference; a cell is one clipped line, so a long snippet still reads in the Detail pane), the three add buttons (above), one Edit dialog covering every kind (`showWhen` on `row.kind`) and a red Delete. `display.label` = `LINK(label, href)` only when there is an href and it is not a task reference — a Task ID is not a URL. The main frame is a vertical split of `tasks` over `references`; the side frame, `task-detail` over `reader`.
- `relations` pane: `mkio-table` on `all_relations`, New / Edit / red Delete (the server's refusal shows inline). `activity` pane: `mkio-table` on `task_activity`, sorted `-event_id`. Both are opened from the Tasks menu rather than living in the default frames.
- **Versions in the UI.** The `tasks` and `references` panes each carry a `history` block, a `_mkio_version` column (mkui labels it "Version" itself) and a History button firing `table.history`; `tasks` also shows `last_event` as **Last Event**. mkui draws Undo and Redo itself, one per configured direction, with `confirm = true`. `history.columns` is named explicitly on both (the tasks one includes `assigned_to`, so a reassignment diffs): left out, mkui would diff the pane's own columns and drag in the derived `score`. **Both Delete dialogs say the delete is permanent and cannot be undone** (`test_ui_config.py` pins the wording). **History** and **Activity** are named apart on purpose: History is a record's versions, with diffs and undo; Activity is what happened to a task, and is never rewritten.
- `task-detail` pane: one `task-refs` widget (`refs.js`), the whole body. mkui draws no toolbar for a widget pane, so the widget draws its own with mkui's classes. **The pane has one cursor**: the task block (`TASK_FIELDS`; an empty value is left out unless it is in `ALWAYS`) or one reference, whichever was clicked last. Add Link / Add Text / Reference Task open the References pane's add dialogs (`dialogs.addLink` / `addText` / `referenceTask`), with or without a task — the dialog asks; Edit follows the cursor, Delete is a reference's alone, History opens either one's versions.
  - **The dialogs are borrowed, not copied**: `dialogs` in app.toml names a pane and a button label, and the widget hands that spec to mkui's `openDialog` — deep-imported from `/mkui/src/widgets/mkui-dialog.js` — so the two places a task or a reference is edited cannot drift. `test_ui_config.py` fails on a `dialogs` entry naming no such button, on the wrong op behind one, and on a key `refs.js` never opens.
  - **The block repaints on the announcement**: mkui republishes `select.state` when a live update lands on the published row, so the cursor and the subtree reset only when the Task ID changes.
  - **The list is the widget's own pair of live queries** — `all_tasks` (three fields, for the parent/child edges) and `task_refs` filtered to the subtree, resubscribed only when the subtree really changes and fenced by a generation counter so a snapshot for the scope just left cannot repaint the one moved to; `mkui-pane-close` unsubscribes both. **The subtree comes from the tasks, not from the Tasks pane's broadcast**, so a complete child's references stay here while the link-filtered References pane drops them.
  - **Snippets are open from the start**, every one: `isOpen` is `flipped.has(id) === snippetsFolded`, where `snippetsFolded` is the pane-wide default ("Fold all" / "Open all" on the Snippets heading, kept in `localStorage` under `FOLD_KEY` through the try/catch `pref`; the one thing refs.js stores — the trail is memory only, and the test holds it there) and `flipped` the snippets clicked away from it, cleared when the task changes. Images and links keep the one-at-a-time `openId`. `openRef` opens either kind for `state.selected_ref`, which now also scrolls its line into view.
  - **Markdown notes render in the task block** (`task.notes_format`), through the same module.
  - **The cursor is published as `state.detail_ref`** (`publishCursor`, from `render`, deduped by row object the way mkui's `publishRow` is, so a live update republishes). Declared in `[state]`; only the Text pane reads it.
  - **A Markdown snippet is rendered by `renderMarkdown` from `richtext.js`** (the bundle's, through the editor's own schema, so it is shown as it was written; the Text pane uses the same) into `div.task-refs-body.task-refs-md`; a plain one stays a `pre`. The schema's `DOMSerializer` builds the nodes, never assigned HTML (`test_ui_config.py` fails on `innerHTML` in `richtext.js`, and on a `markdown.js` coming back); raw HTML in the Markdown passes through the schema, a link outside `SAFE_PROTOCOLS` is shown as its text, and `.task-refs-md` is `pre-wrap`, as the editor is, so a single newline is a line break.
  - Sections: one per relation wording, then Snippets / Images / Files / Links, counted (`sectionOf` splits an image off the files by its stored `mime`, so the section is presentation, not a fifth kind). Within a section the selected task's own come first, then each descendant's, tagged `from <Task ID>`. **Images are a grid of tiles**, the thumbnail being the file itself: mktask stores no derived images. A clicked tile opens full size below the grid.
  - `state.selected_ref` **marks** a line, opens it and takes the cursor — only a reference this pane lists, and only once per selection (`appliedRefId`), so a line closed by hand stays closed. A delete is announced with the request's data (a `ref_id`, no `task_id`), so `onUpdate` matches a delete by id and an insert by scope. `onUpdate` also reads mkio's third `info` argument, so a row moved by an undo says so in the status line.
  - **Go to leaves a trail**: `back` / `forward`, in memory, `TRAIL_MAX` places of `{ task_id, ref_id }`. Only a Go to that lands pushes (and empties `forward`); the two chevrons that lead the toolbar (mkui's `icon`, deep-imported from `/mkui/src/lib/icons.js`) `step` along it through the same `jump` Go to uses, passing over a deleted task. `pending` puts the cursor back on the line left from once the references arrive.
  - **"Go to" and History are `table.select`** on the pane that owns the record: mkui's `selectRows` runs the same `publishSelection` a click does, so the linked panes follow with no further code, and `fireAction` returns `{ ok, selected, missing, hidden }` to report. `reveal` clears the status filter and retries once when a filter hides the target. History then fires `table.history`, which would select the record itself but reports only whether the pane has a history block, not whether the record was reachable — hence selecting first.
- `text` pane (0.21.0): one `text-pane` widget (`textpane.js`), on the Tasks menu and under Detail in the default frames. **It shows the text and nothing else**: a task's notes, a snippet's body (Markdown rendered, plain as written), an image as itself, and nothing for a link, a file or a task reference (`itemOf`). It follows three sources (`SOURCES`): `selected_task`, `selected_ref` and `detail_ref`. **"Last picked" is the source that moved to a different record most recently**; a republish of the same record repaints in place and never takes the pane. `detail_ref` going empty always means the task — the Detail pane republishes a References selection as `detail_ref` *before* the pane hears `selected_ref` (subscription order), so following `current === source` alone would leave it on the reference when the task block is clicked.
  - **A click edits in place** (not on a link, not after a drag-select): `mountRichText` takes the view's place, **laid out as a dialog is**: under the text, the toolbar (the richtext field puts it under its text everywhere, so opening an editor never moves a word), then status / Cancel / Save in a row of their own (`textpane-foot`), as in a dialog's footer. The widget fills the pane (`mkui-pane-content` has a fixed height) and the text scrolls in its own box, so neither row ever covers a word; the view and the editor share padding, size and line height, so `posAtCoords` at the click puts the cursor on the character clicked. **The edit stays open until Save (Cmd/Ctrl+Enter) or Cancel (Escape)**: a new pick is recorded but not shown ("Save or cancel to move on"), and a live update to the record being edited is not applied ("Changed elsewhere — saving replaces it"). A plain item opens in a `literal` editor and is saved as Markdown. A save with nothing typed only closes; a refused one keeps the text and shows the reason.
  - **A save writes the text alone**: `edit_notes` (its own steps: notes, notes_format, updated_at, last_event — `edit` takes every field and would write back the others as the pane last saw them) and `edit_snippet` (Python only, through `edit_ref`'s steps: refuses any other kind, keeps a typed label, and moves an automatic one — equal to `default_label` of the old text — to the new first line). One save, one version. Its classes are `textpane-*`, each with a rule (the test reads them out of the file).
- **The statusbar's right text is a template**: `mktask` followed by `state.mkio.server.version`, the version the server announced in its `_mkio` reply, so the UI never carries a version of its own. `IF(...)` keeps the trailing space off until the reply lands. `test_ui_config.py` pins the template. **Help → About** (last) is `dialog.about`, built from `app` (`description`, `copyright`, `links`) over mkui's facts (`about.builtins`: server, mkui, mkio). `app` has no `version` for the same reason: `app.about.heading` is this same template (pinned). **Keyboard Shortcuts** above it is `dialog.open` on top-level `dialogs.shortcuts`, a `facts` box; the test holds every menu `shortcut` hint to a line, and the last says Undo/Redo have none.
- Menubar `Configure`: `pane.show` for `relations` and `assignees` — the two lists that are settings rather than work. It sits between Edit and Layout, and `test_ui_config.py` pins that position and that neither pane is still on the Tasks menu. Menubar `Tasks`: `pane.show` for the working panes (every pane is on some menu — the test insists) and nothing else (`test_ui_config.py` fails on any `table.filter` or `table.expand` menu item). Menubar `Edit`: `edit.undo` / `edit.redo`.
- `test_ui_config.py` checks every dialog/button field against the op's `fields` + `key` (scratch `_x` and readonly fields are never sent; every field or key without a `defaults` entry must be sent); that per table pane `${row.x}`, `values`, `styles`, `display`, `sort`, `filters`, `tree` and text-widget `state.x` name real columns and declared state; that every non-text widget type is registered by a module index.html imports; that `refs.js` only calls declared reqreps/ops/state; that every pane is in the default frames or on a menu; and the `history` blocks — mkui's key set, the services they name, each feed's `__history` table and filterable key, that every action name is one mkui registers; and the About/message-box keys, `builtins` names and mkui floor against the installed mkui. **Add the column to `mktask.toml` before using it in the UI.**

## Versioning and release

`mktask/__init__.py` `__version__` is the single source of truth (hatch dynamic version). `pyproject.toml` pins `mkio>=1.6.0,<2` (expression language 2; served files revalidate) and `mkui>=1.13.0,<2` (`dialog.about` `builtins`; the header caret's second shift-click; `visible`). **Platforms**: Linux, macOS and Windows on CPython 3.11+. `_check_port` sets `SO_REUSEADDR` only off Windows, where it would bind over a live listener and let a busy port pass. `_unlink_orphans` swallows any `OSError`: on Windows a file being served raises `PermissionError`. Every text read or write names `encoding="utf-8"` (only the tests have any), `.gitattributes` pins LF, and `relations.json` stays ASCII because mkio's seed loader reads it in the default encoding; `test_platform.py` guards all three. Release (`/cut`): bump it, update README/CLAUDE/tests, commit as `Release vX.Y.Z: summary`, push, `rm -f dist/*; python -m build`, `twine upload dist/*`, `pip install --upgrade mktask`. No git tags, matching mkfix.
