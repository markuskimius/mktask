# mktask

Work task prioritizer built on [mkio](https://github.com/markuskimius/mkio) (config-driven microservice backend: SQLite + WebSocket services) and [mkui](https://github.com/markuskimius/mkui) (config-driven Web Components workspace). Sibling of [mkfix](../mkfix), whose structure this repo copies.

## Quick start

```bash
pip install -e '.[test]'
mktask                    # http://127.0.0.1:8080/, mktask.db in cwd
mktask -d :memory: -p 9090 --user mark
mktask --files ~/refs     # uploaded reference files (default: <db>.files beside the database)
python -m pytest
```

## Architecture

- `serve()` in `__main__.py` loads `mktask.toml` via `mkio.config.load_config`, injects `version = __version__`, resolves `"__mkui__"` to `mkui.static_dir` and relative static dirs against the TOML's directory, sets `services.tasks.prefix` from `user` (`--user`, default `getpass.getuser()`), resolves the files directory (`_files_dir`: `--files`, else `<db_path>.files`, else a temp dir for `:memory:`), creates it, adds it as the `/files` static route and as `services.tasks.files_dir`, probes the port (`_check_port`), then `create_app(cfg, routes=[("POST", "/files", …)]).run()`. A startup hook prints the banner. Neither the username nor the files dir is a top-level mkio config key (unknown keys warn); tests that call `serve()` chdir to a scratch dir because it creates the files directory.
- `POST /files` (`_upload_handler`): raw body, `Content-Type` → extension (`_EXTENSIONS` overrides, then `mimetypes`, else `.bin`), streamed under `MAX_UPLOAD` (20 MB) rather than aiohttp's 1 MB `client_max_size`, written as `<sha256>.<ext>` (temp + `os.replace`), returns `{href, mime, size}`. Content-addressed: repeats dedupe, no client name reaches the filesystem. The route never writes a row; the client follows with `add_ref`.
- `_check_port` runs before `create_app`: a bind failure inside `app.start()` happens after the startup hooks have opened the database, whose aiosqlite threads then keep the process alive after the traceback. The probe turns that hang into an exit-1 with a one-line error (`test_port_in_use_fails_cleanly`).
- `_find_config()` prefers `./mktask.toml` over the packaged one, so a user can copy the TOML out and customize it.
- The UI is JSON, not TOML: `index.html` fetches `/static/app.json` with `cache: "no-cache"` (mkio serves statics without Cache-Control) and calls `setConfig`. No `[config]` route in the TOML.
- `mkio.expect` in app.json pins `name` and `expr` only. Never pin `version` — every release would then show "Server mismatch" (`test_ui_config.py` guards this).

## Vocabulary

A task is **split** into **child** tasks (never "subtask"); a child can be split again, to any depth. A task is **moved** when its parent changes: under another task, or to the **top level** (no parent). A task is **open** or **complete** (never "done"). Its identifier is its **Task ID** (never "ID"). A task has **references** (never "attachment"): a **URL**, a **text** snippet, a **file**, or a **task link** with a **relation**; the other end is the **linked task**. "Link" means only a task-to-task reference. A relation is a **pair of wordings**, **forward** ("blocks", this task to that one) and **backward** ("blocked by"), equal for a symmetric relation ("relates to"); the user defines them. Every change to a task or a reference makes a new **version** of it; **undo** and **redo** step it back and forth along its versions (never "revert"). What happened to a task — created, moved, ref_added — is its **activity**, kept apart from its versions. `test_ui_config.py` fails on the word "done" anywhere in app.json or the TOML.

## Data model

`tasks`: `task_id` (TEXT PK), `parent_task_id` (`''` = top level, else the parent's Task ID), `title`, `notes`, `status` (`open` | `complete`), `importance` and `urgency` (1..5), `due` (ISO date or `''`), `created_at` / `updated_at` / `completed_at` (UTC `YYYY-MM-DD HH:MM:SS`, matching SQLite's `CURRENT_TIMESTAMP`). Timestamps on update come from the client: buttons and the Edit dialog send `${TIME(NOW(), '%Y-%m-%d %H:%M:%S')}` (mkio expression stdlib, UTC by default) because mkio transaction `defaults` are static values.

`relations`: `relation_id` (AUTOINCREMENT), `forward`, `backward` (= `forward` when symmetric), `notes`, timestamps. Every wording is unique across both columns, case-insensitively (service-enforced; mkio has no unique index). Seeded from `relations.json` (beside the TOML; mkio resolves `seed` against the config's directory and seeds only when it first creates the table). `SEED_RELATIONS` in services.py is the path; tests read it for the wordings.

`task_refs`: `ref_id` (`INTEGER PRIMARY KEY AUTOINCREMENT`; nobody refers to a reference by name), `task_id` (the owner), `kind` (`url` | `text` | `file` | `task`), `relation` (task links only: a **wording** from `relations`, e.g. `blocked by`, else `''` — the wording itself, not an id, so no join is needed and a rename rewrites the rows), `label` (what the UI shows), `href` (`url`: the URL; `file`: `/files/<sha256>.<ext>`; `task`: the linked Task ID; `text`: `''`), `body` (`text` only), `mime` (`file` only), `created_at` / `updated_at`. One-to-many: a reference belongs to one task; the same URL or file under two tasks is two rows, and for files that is what keeps a shared file alive (`_unlink_orphans` counts rows by `href`). **A task link is two mirrored rows**, one per side with the pair's two wordings, so a pane filtered on `task_id` shows every link of a task from its own side with no client logic — mkio's live updates cannot carry joined columns, which is why links are not a separate table. `href` means three things by kind; `display.label` in app.json branches on `kind` because a Task ID is not a hyperlink. Files live on disk, never in SQLite (query subscribers receive whole rows).

`tasks.last_event` is the most recent thing to have happened to the task, in words — "Created", "Split into Wire the pane", "Attached a file: shot.png", "Linked: blocks TKMA00000002", "Moved under TKMA00000007". `event_phrase(action, detail, kind)` in services.py builds it, and `_event()` carries it alongside the `task_events` row it makes, so an event and the Last Event it sets are never worded in two places. Because `tasks` is versioned it rides along in every recorded version, which is what makes a task's history say what each version was *about* — `_mkio_op` only ever says `insert` or `update`.

**How `last_event` is written matters.** For an op that already writes the task row it is one of that op's own fields (`_rows_for` puts it there); a separate update in the same transaction would record a *second* version of the same task. For an op that does not — a reference added, edited or deleted, and the parent's side of a split — it is the `touch` op, one per task, applied through `_touch_steps(events, wrote)` where `wrote` names the tasks the op wrote itself. **The touch is what puts reference events in a task's recorded history**, and because it carries the same `_mkio_ref` it is part of the same action to undo: undoing a reference steps the task's version back with it. **The undo/redo hook never touches it** — an undo restores the version's own `last_event`, and writing one would extend the chain past the cursor and discard the redo branch the undo had just made.

`counters`: one row `name = "task"`, `last` = the last Task ID number issued.

**`tasks` and `task_refs` are `versioned = true`** (mkio ≥ 0.5). mkio gives each a `_mkio_version` counter and a companion `tasks__history` / `task_refs__history` keyed `(pk…, _mkio_version)`, holding every version's whole row stamped with `_mkio_op` (`insert` / `update` / `baseline`), `_mkio_ref` (the transaction), `_mkio_user` and `_mkio_service`. The live row's counter is a **cursor** into that chain: versions above it are the redo branch, and writing at version V discards V and above — an edit after an undo abandons what was undone. **A delete is a real delete**: mkio drops the row's history with the row, which is why deleting is the one thing here that cannot be undone. `_mkio_user` stays NULL because mktask has no auth; the actor is recorded in `task_events` instead. Nothing in mktask.toml declares these tables — mkio derives them, and `auto_migrate` creates them.

`task_events`: `event_id` (AUTOINCREMENT), `task_id` (the owner), `action` (`created` | `split_from` | `split_to` | `edited` | `moved` | `completed` | `reopened` | `ref_added` | `ref_edited` | `ref_deleted` | `undone` | `redone`), `detail` (one line — the new title, the new parent, the reference's label), `ref_id` (the reference an event concerns, `0` when there is none or when an insert's key is not yet known), `actor` (`--user`), `at`. **Deliberately not versioned**: it is append-only, it must survive the redo-branch truncation a post-undo edit performs, and it records events that change no row of their own. The transaction ref is mkio's own `_mkio_ref` column, so no column of ours repeats it. A task delete takes its subtree's events with it.

**Task IDs** are `TK` + two prefix letters + a decimal sequence padded to at least 8 digits (`TKMA00000001`; pattern `^TK[A-Z0-9]{2}\d{8,}$`). The prefix is `user_prefix(username)`: alphanumerics, uppercased, first two, `X`-padded. The sequence is global (one counter regardless of prefix), never reused after a delete, and never wraps: `TKMA99999999` → `TKMA100000000`. Nothing may depend on id order (text order breaks at the rollover); chronology is `created_at`.

The `score` column is virtual: `values.score = "importance * urgency"` on the `tasks` pane. It is the placeholder for the real prioritization model (see PLAN.md, Deferred).

**No migrations before 1.0.** A schema change means "delete mktask.db"; the README says so. `auto_migrate = true` only covers additive changes — which 0.8.0's were: an existing database gains `last_event`, `task_events` and the two history tables on first start, and mkio records every row already there as a `baseline` version 1 so a first edit is undoable. `TestUpgrade` in test_server.py builds a pre-0.8.0 database from the current config minus what 0.8.0 added and boots the server on it, so that promise cannot rot.

## Services (`mktask.toml`)

- `tasks` — `protocol = "mktask.services.TaskTransactions"`, a `TransactionService` subclass; the ops stay in the TOML. `add` and `split` are two steps (upsert `counters.last`, insert the task) plus their events: the class takes the next number from an in-memory counter (seeded in `start()` from `counters`, else from the largest existing Task ID), injects `task_id` and `last` into the data, rejects a request that carries its own `task_id`, and rejects a `split` whose `parent_task_id` is not an existing task (no orphans; a rejected request consumes no number). The `task_id = ""` / `last = 0` defaults exist only so mkio treats them as optional for the client. Every op goes through `_guarded` → `_op_<name>` — `add` and `split` included, so every op fills its own `task_events` rows the same way — replying mkio-style (`KeyError` → "Missing required field", anything else → its message). **Events are always filled in Python, never bound.** A `bind`'s `"$N.field"` is an absolute position in the request's op list, and `_steps` repeats an op set once per row for a cascade or a link's mirror, so a bound event would name the first row's write for every row; `_submit` and `_submit_each` take an `events=` list and append `add_event` steps to the same transaction (on `_submit_each` they ride the first request — one batch, one commit, and which request carries them makes no difference to what lands). `complete` runs the single-row op over the subtree (recursive CTE, parents first), `reopen` over the task and its ancestors, in one `writer.submit` (`_submit`) so the change bus announces every RETURNING row. **Deletes go one request per row** (`_submit_each`, gathered so they land in one batch): mkio announces a delete with the request's `data`, so one request for a subtree announced the parent's Task ID for every row and a live table kept the children (`test_subtree_delete_announces_every_row`). `delete` also removes every reference the subtree owns or is linked to (`task_id IN subtree OR (kind = 'task' AND href IN subtree)`), then unlinks orphaned files. `edit` is the plain update plus a `relabel_ref` per link that points at the task (same submit). `move` rewrites one row's `parent_task_id` (`''` or `TOP_LEVEL` = top level; a Task ID encodes no hierarchy, so nothing else is rewritten and the subtree follows for free): it refuses self, an unknown parent, and a parent inside the moved subtree, refuses a move that would leave a task link inside one tree (`_check_no_links_merge`: any `kind = 'task'` row from the moved subtree into the new parent's root subtree — `add_ref` forbids such a link, so a move must not create one behind the user's back; the message names the first and counts them), and appends the `reopen` steps for the complete new ancestors when the moved subtree holds open work, in the same submit. `add_ref` requires the owning task, fills a missing label (`default_label`), forces `href`/`body` by kind, and for kind `task` checks the relation is a known wording (`_inverse` looks the pair up; the mirror gets the other wording), self, target, same tree (splitting already relates a task to its ancestors, descendants, and every descendant of an ancestor: the two `_ancestors_and_self` chains must end in different roots; ancestor and descendant get their own messages), and duplicate, then inserts the row and its mirror; `edit_ref` on a task link takes only `relation` and rewrites both halves (`_mirror` finds the other), on a file keeps the `href`, on a snippet blanks it; `delete_ref` deletes the mirror too, then the file if nothing names it. `add_relation` / `edit_relation` (`_relation_data`: trim, backward defaults to forward, uniqueness across both columns excluding self) / `delete_relation` (refused while any link carries either wording, count in the message); a rename rewrites `task_refs.relation` through `reword_ref` in the same submit. `relabel_ref` and `reword_ref` exist for the service, not the UI. mkio skips op validation for dotted protocols; `test_ui_config.py` and `test_server.py` are what catch a bad field name.
- `all_tasks` — query on `tasks`, `filterable = ["status", "parent_task_id"]`. The blotter subscribes to this, and so does the Detail pane's `task-refs` widget (unfiltered, `fields = task_id/parent_task_id/title`) for the parent/child edges its subtree needs.
- `task_refs` — query on `task_refs`, `filterable = ["task_id", "kind", "relation"]`; the References pane subscribes, and so does the Detail pane's `task-refs` widget (filtered to the selected task's subtree: `task_id == 'X'` for one, `CONTAINS([…], task_id)` for many — `filterable` gates *whether* a filter is honoured, not which expression, and a filtered query still announces a delete of a row it had sent, which is how a deleted reference leaves the widget). `all_relations` — query for the Relations pane. Two reqreps feed the Reference dialog's `optionsFrom`: `relation_options` (every wording as `value`/`label`, `UNION` collapsing a symmetric pair to one) and `task_options` (open tasks outside `:task_id`'s tree — a recursive CTE climbs to the root, another expands it). `move_options` feeds the Move dialog's parent picker: `__top__` (`— Top level —`, ordered first by a subquery's `ord`) plus every open task outside `:task_id`'s own subtree. **The top level is a sentinel, not `''`**: mkui's `optionsFrom` prepends its own empty "nothing chosen" option and then forces the selection back to `""` (it cannot preselect a value), so with `''` the two entries would be one and an untouched dialog would silently promote the task. `TOP_LEVEL` in services.py maps it back to `''`; `required` on the field refuses the empty option. `test_ui_config.py` fails on a reqrep nothing names and on a name that is not a reqrep, so neither side goes stale. A query with a JOIN would not update live (mkio publishes the bare primary-table row and drops secondary-table changes), so nothing joins.
- `task_activity` — query on `task_events`, `filterable = ["task_id", "action"]`; the Activity pane subscribes and follows the Tasks selection through table linking, the way the References pane does. `task_versions` / `ref_versions` — queries on `tasks__history` / `task_refs__history`, filterable on the base primary key, which is what mkui's history pane narrows to one record with. `task_version_state` / `ref_version_state` — reqreps returning `{ current, top }` so mkui can tell whether a redo is there to offer; written as two subqueries so they answer with one row even when the record has been undone out of existence (`current` NULL). `task_version_chain` / `ref_version_chain` — reqreps returning one record's whole chain, which mkui reads to spell out what a step will change in its confirmation. mkio never advertises a history table, so these services are the deliberate act of exposing it; transaction ops against one are rejected at config load, so the exposure is read-only by construction.
- `mkui_layouts`, `mkui_layouts_list`, `mkui_layouts_get` — verbatim from mkui's scaffold; mktask has no login so every save lands under owner `''`.

## History, undo and redo

**mkio owns the version log and mkui owns the history UI; mktask owns what neither can know.** A `history` block on a table pane (`table`, `key`, `feed`, `versions`, `state`, `columns`, `undo`, `redo`, `confirm`) is all mkui needs to draw the `mkio-history` pane — the versions in a real `mkio-table` with **Diff** and **Blame** panels — plus an Undo and a Redo button on the source pane's toolbar. `table.history` opens it (`{ pane, keys }`, the keys selecting the record first); `workspace.showPaneHistory` registers `_history:<pane>` on demand, titled "History — <title>", one per table pane and re-pointed as the selection moves. **mkui drops an unknown `history` key with a console warning rather than failing**, so `test_ui_config.py` is the only thing that catches a typo in one.

Three things mktask adds:

- **`undo_action` / `redo_action`** (`_step_action`). mkio's `undo`/`redo` op types move **one row's** cursor, keyed by primary key; a mktask action is rarely one row — a link is two mirrored rows, completing a task completes its subtree, a move reopens the ancestors it lands under. The group needs no bookkeeping of ours: mkio stamps every row a transaction writes with that transaction's `_mkio_ref` and indexes it, so `_group_ref` finds the ref that wrote the version being stepped off (for a redo, the one *above* the cursor, or version 1 when there is no row) and `_group_rows` takes everything it wrote. **The steps go one request per row**, because the writer reads an undo's key from the request's own `data`, not from its params; they are gathered, so they land in one batch and one commit. `history.undo` in app.json points at these, never at mkio's own ops — those (`undo_task`, `redo_task`, `undo_ref`, `redo_ref`) exist only for `_step_action` to submit.
- **Three guards** (`_check_step`). A step is refused rather than half-applied when a row of the group has moved past the version the action wrote (`_mkio_version` no longer matches — the way to produce this is mkio's raw per-row op, which is what the test does), when an undo at version 1 would remove a task that still has children or references (`_check_removable`), or when the version being stepped onto names a parent or a linked task that has since been deleted (`_check_restorable`). Messages stay short: mkui clips a dialog's status line to one row.
- **`undo_redo_hook`**, registered in `serve()` through mkio's `on_undo_redo`. Moving a cursor restores the row but not what followed from the write it reverses, and neither of these is on a cursor move's path: a link shows the title of the task it points at (refreshed by `_op_edit`, so a step would leave it stale), and the narrative. It relabels through `_relabel_steps`, which **only touches rows whose label disagrees** — a relabel is an ordinary write on a versioned table, so a no-op one would spend a version and discard that reference's redo branch, and being idempotent is what lets the hook run it blindly after a group step that already carried the link rows along. Only a `tasks` step is narrated: a reference's own steps are its version history's to tell, and narrating them would put a "redone" in a task's activity for the resurrection `_op_delete` does on its way to deleting a reference for good. A row undone out of existence is not narrated at all — there is nothing left to narrate it against. The hook must be registered **before** `start()` (mkio raises otherwise) while `app.services` is empty until after, so `serve()` looks the service up per event rather than capturing it. `cause` is its own recursion guard: the hook's own writes are ordinary ones, so their events carry `cause = None`.

**Deletes are permanent and thorough.** `_op_delete` resurrects (`redo_ref`) any reference of the subtree left as a chain by an undo, so deleting it drops that chain the way mkio drops any deleted row's history; then deletes every reference the subtree owns *or that points at it* (the same `task_id IN … OR (kind = 'task' AND href IN …)` reach, written once and used for both the live rows and the recorded versions), the tasks, and the subtree's events. `_unlink_orphans` now keeps a file while **either** a live `task_refs` row or a `task_refs__history` row names it — an undone file reference is a chain with no row, and redo has to find its file still there — so a blob outlives its last reference only for as long as something could bring that reference back. **Undo never unlinks**; only a delete does.

**No keyboard shortcut.** mkui registers `edit.undo` / `edit.redo` and binds no key on purpose — "this writes to state everyone shares" — and mktask follows it. The menubar's Edit menu fires those actions; the toolbar buttons are the primary path.

## UI (`app.json`)

- `tasks` pane: `mkio-table` with `tree` on `parent_task_id`/`task_id`, sort `["-score", "created_at"]`, `select.state = "selected_task"`. `filterScope = "all"` (Branch) makes the default filter `status = ["open"]` test every row while keeping the way to a match, so a complete child under an open parent is hidden and an open child keeps its complete parent visible. Buttons: New, Edit, Move, Split, Reference, History, Complete, Reopen, Delete. **mkui renders a dialog's status line `nowrap` with an ellipsis** — a server refusal longer than the footer is silently cut in half, which is why Move is `width = 600` and `_check_no_links_merge`'s message is as short as it is. **Delete's readonly-line dialog *is* the confirmation** (mkui has no confirm on transaction buttons); its `style` rule paints it red only `when = "enabled"`, with no bold/caps so its width never shifts. No dialog ever sends `task_id` or `last` on add/split.
- The one `Reference` button's dialog covers every kind (live dialogs, mkui ≥ 0.2.21). **Underscore-named fields are scratch and are never submitted; a field hidden by `showWhen` is not submitted either** — which is why `href`/`body`/`relation`/`label` carry `defaults` on `add_ref`/`edit_ref`. There is no file field in mkui, so files stay with the Detail pane's drop box. Readonly lines carry no `name` (mkui ≥ 0.2.22; 0.2.21 blanked nameless ones).
- **The References and Activity panes follow the Tasks selection through mkui table linking**: `tasks` broadcasts `task_id`, they listen on it, and the selected rows' Task IDs become an include filter on the listener (a selected tree row sends its subtree since mkui 0.2.20; nothing selected retracts the filter). All set `link.chips = false` to keep the control chips off the toolbars. Nothing in `refs.js` filters anything — its query is filtered server-side.
- `references` pane: `mkio-table` on `task_refs`, `select.state = "selected_ref"`, sorted `-created_at`, one Edit dialog covering every kind (`showWhen` on `row.kind`) and a red Delete. `display.label` = `LINK(label, href)` only when there is an href and it is not a task link — a Task ID is not a URL. The main frame is a vertical split of `tasks` over `references`.
- `relations` pane: `mkio-table` on `all_relations`, New / Edit / red Delete (the server's refusal shows inline). `activity` pane: `mkio-table` on `task_activity`, sorted `-event_id`. Both are opened from the Tasks menu rather than living in the default frames.
- **Versions in the UI.** The `tasks` and `references` panes each carry a `history` block, a `_mkio_version` column (mkui labels it "Version" itself — it is in `SHOWABLE_COLUMNS`) and a History button firing `table.history`; `tasks` also shows `last_event` as **Last Event**. mkui draws Undo and Redo itself, one per configured direction, with `confirm = true`. `history.columns` is named explicitly on both: left out, mkui would diff the pane's own columns and drag in the derived `score`. **Both Delete dialogs say the delete is permanent and cannot be undone** — the one asymmetry in an app where everything else steps back — and `test_ui_config.py` pins that wording. **History** and **Activity** are named apart on purpose: History is what a record looked like over time, with diffs and undo; Activity is what happened to a task, references included, and is never rewritten.
- `task-detail` pane: one `task-refs` widget (`refs.js`), the whole body. mkui draws no toolbar for a widget pane, so the widget draws its own with mkui's classes. **The pane has one cursor**: the task block (`TASK_FIELDS`; an empty value is left out unless it is in `ALWAYS`) or one reference, whichever was clicked last. Edit follows the cursor, Delete is a reference's alone, History opens either one's versions.
  - **The dialogs are borrowed, not copied**: `dialogs` in app.json names a pane and a button label, and the widget hands that spec to mkui's `openDialog` — deep-imported from `/mkui/src/widgets/mkui-dialog.js`, the way mkio-table loads it, because mkui does not re-export it — so the two places a task or a reference is edited cannot drift. `test_ui_config.py` fails on a `dialogs` entry naming no such button, on the wrong op behind one, and on a key `refs.js` never opens.
  - **The block repaints on the announcement**: mkui republishes `select.state` when a live update lands on the published row, so the cursor and the subtree reset only when the Task ID changes.
  - **The list is the widget's own pair of live queries** — `all_tasks` (three fields, for the parent/child edges) and `task_refs` filtered to the subtree, resubscribed only when the subtree really changes and fenced by a generation counter so a snapshot for the scope just left cannot repaint the one moved to; `mkui-pane-close` unsubscribes both. mkio-table is not the only thing allowed to subscribe, and a pane answering "what does this task, and the work under it, refer to?" must not depend on another pane's cursor. **The subtree comes from the tasks, not from the Tasks pane's broadcast**, so a complete child's references stay here while the link-filtered References pane drops them.
  - Sections: one per relation wording, then Snippets / Images / Files / URLs, counted (`sectionOf` splits an image off the files by its stored `mime`, so the section is presentation, not a fifth kind). Within a section the selected task's own come first, then each descendant's, tagged `from <Task ID>`. **Images are a grid of tiles**, the thumbnail being the file itself — mktask stores no derived images, and a screenshot is small enough that a second copy would cost more than it saves; a 12-megapixel habit is what would earn a `GET /files/<hash>?w=` route. Clicking a tile opens it full size below the grid, one at a time.
  - `state.selected_ref` **marks** a line, opens it and takes the cursor — only a reference this pane lists, and only once per selection (`appliedRefId`), so a line closed by hand stays closed. A delete is announced with the request's data (a `ref_id`, no `task_id`), so `onUpdate` matches a delete by id and an insert by scope. `onUpdate` also reads mkio 0.5's third `info` argument, so a row moved by an undo says so in the status line.
  - **"Go to" and History are `table.select`** on the pane that owns the record: mkui's `selectRows` runs the same `publishSelection` a click does, so the linked panes follow with no further code, and `fireAction` returns `{ ok, selected, missing, hidden }` to report. `reveal` clears the status filter and retries once when a filter hides the target. History then fires `table.history`, which would select the record itself but reports only whether the pane has a history block, not whether the record was reachable — hence selecting first.
- Menubar `Tasks`: `pane.show` for every pane (the test insists), `table.filter` entries (`{"status": ["open"]}` with `merge`; `{"status": null}` clears it) and `table.expand` (`depth = "all"` expands, no `depth` collapses — there is no separate collapse action). Menubar `Edit`: `edit.undo` / `edit.redo`.
- `test_ui_config.py` checks every dialog/button field against the op's `fields` + `key` (scratch `_x` and readonly fields are never sent; every field or key without a `defaults` entry must be sent); that per table pane `${row.x}`, `values`, `styles`, `display`, `sort`, `filters`, `tree` and text-widget `state.x` name real columns and declared state; that every non-text widget type is registered by a module index.html imports; that `refs.js` only calls declared reqreps/ops/state; that every pane is in the default frames or reachable from the Tasks menu; and the `history` blocks — mkui's key set, the services they name, each feed's `__history` table and filterable key, and that every action name is one mkui registers. **Add the column to `mktask.toml` before using it in the UI.**

## Versioning and release

`mktask/__init__.py` `__version__` is the single source of truth (hatch dynamic version). Release (`/cut`): bump it, update README/CLAUDE/tests, commit as `Release vX.Y.Z: summary`, push, `rm -f dist/*; python -m build`, `twine upload dist/*`, then `pip install --upgrade mktask` so the user's venv runs the published wheel (siblings mkfix/mkui are installed non-editable there; mkio is editable). No git tags, matching mkfix.
